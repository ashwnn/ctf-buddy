# Predict service credentials from a weakly seeded PRNG

**First useful action.** Trace how the authorization code is generated in the source, then reproduce
the same generator locally and check whether your model predicts a value the service actually issued.

```bash
grep -rIn -E "(rand|random|srand|mt_rand|Random|seed|token|auth_?code)" <SERVICE_SRC> | head -n 60
```

Expected: the code path that produces the code plus its seed source. If generation is not present in
the service you can read, look for it in a library call or a template engine instead of assuming the
generator is cryptographically secure.

## Symptoms

- Authorization codes reset to known values, repeat across accounts, or form a small observed set.
- The service uses a general-purpose random API where a security token is expected.
- Two instances restarted at the same moment produce the same code sequence.

## Prerequisites and assumptions

- Source access (or enough samples) for the generator, plus a *local* instance of the service for
  reproduction. Cross-team use requires the organizer's explicit scope confirmation.
- Precision about the mechanism: this card is about *predictable generation*, not about "weak crypto" in
  the abstract. The corpus records one real case where a competitor's token construction was
  service-specific PHP/PRNG logic and where the recommended-looking "change the seed" fix was kept only
  as an event example and explicitly *not* recommended as cryptography.
- A local fixture URL such as `http://127.0.0.1:<PORT>` for the reproduction.

## Diagnostic sequence

1. Locate the generator and its seed. Distinguish never-seeded (implicit default), time-seeded,
   PID-seeded, and process-global-state seeds; each predicts differently.
2. Reproduce it locally: implement the same construction with the same seed source and compare against
   real values you obtained from your *own* service.
3. Ask a discriminating question: which observable output reveals or constrains the next value? If
   nothing observable correlates, the prediction model is not yet usable — go back to the generator
   trace instead of brute-forcing the network.
4. Only after the model reproduces known values, predict a *future* value and confirm it against your
   local instance.
5. Then and only then consider using the primitive offensively, and only within confirmed scope.

If the model reproduces known values → treat the token construction as broken and fix the generation
path (below). If it does not → the seed includes entropy you have not modelled (PID, monotonic clock
with unknown offset, per-request re-seed); document and stop rather than escalating to enumeration.

## Commands and interpretation

| Command | Reads as | Means |
|---|---|---|
| source grep for the random API | call site + arguments | Identifies generator family and whether a seed is passed |
| source grep for seed assignment | constant, time, or PID | Determines how much attacker knowledge is needed |
| local reproduction script | matches known issued values | Prediction model validated: escalate carefully |
| local reproduction mismatch | no match | Unmodelled entropy: do not proceed to network enumeration |

## State-changing actions

- **Impact:** replacing the token generator changes every credential the service issues; stored or
  in-flight values generated by the old path remain valid in the database unless handled.
- **Preconditions:** a reproducible prediction against the local fixture, plus knowledge of what the
  checker requires from this feature (login path, single-use behaviour, token length if the client
  parses it).
- **Health check before:** `curl -s http://127.0.0.1:<PORT>/<LEGITIMATE_ENDPOINT>` — expect the known
  legitimate response your baseline recorded.
- **Apply:** the narrowest change that removes predictability: delegate code generation to the platform's
  cryptographically secure generator with sufficient output length, keeping the existing storage,
  transmission, and comparison logic untouched.
- **Health check after:** rerun the same request — expect the same legitimate response shape; regression
  probe: complete a full legitimate issue-and-use cycle and confirm old codes stored before the change
  still verify.
- **Rollback:** restore the previous generator commit and restart the service; if the platform has no
  CSPRNG available, keep the old generator and reduce exposure instead (shorter validity, server-side
  binding) rather than improvising an unvetted scheme.

## Exploit → patch pair

- **Flaw:** a security decision consumes output from a deterministic generator whose internal state is
  recoverable from public values, so an attacker can compute a valid code.
- **Reproduce on the isolated fixture:** run the local reproduction script against
  `http://127.0.0.1:<PORT>` → the predicted code is accepted for a second account within the same
  process lifetime.
- **Narrow patch:** replace only the code-generation call with a cryptographically secure generator; do
  not touch the validation path, storage schema, or response format.
- **Legitimate functionality that must keep working:** issuing a code to a user and using it to
  authenticate, including codes issued before the patch.
- **Verify:** predicted code now rejected **and** a freshly issued legitimate code still authenticates.

## Failure modes and things teams stopped doing

- "Fixing" predictability by changing the constant seed. The corpus records this explicitly: one team's
  seed-change patch is preserved as an event anecdote and *not* recommended as cryptography. A new seed
  is still a deterministic generator, and the next team may recover it again.
- Network brute force before local modelling. Every unvalidated guess sent to a target costs requests in
  a timed event and can break service availability, which costs availability points in A/D formats.
- Reading the token as an encoded value and trying to decode it, instead of asking where it came from;
  see `card-crypto-classify-before-decoding`.
- Assuming all generators in a service are the same one. A common entropy source for cosmetic features
  does not prove the session token uses it.
